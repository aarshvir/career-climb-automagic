# Job-loop parity: the product Jobvance needs to become

Reviewed 11 October 2026. This is a source review and implementation contract, not a report that a job loop has been executed. The reviewed `cv`, `job-loop` and `job-loop-2` source copies were supplied separately; the full-loop copy includes a later shared-bundle revision and is not asserted to be the exact earlier email snapshot. No personal career record, mailbox content, private figures, contact identifiers or CV examples are reproduced here. No Python attachment, search, mailbox action, draft creation or application was executed for this review.

The intended audience is students applying for jobs, MBA students and busy professionals changing roles. The intended product is a profile-driven preparation and job-search loop: understand the person's record, review incoming activity, find and verify opportunities, prepare grounded materials, maintain continuity and present the next actions. A one-vacancy CV wording comparison is a useful component, but is not parity with either original loop.

## Current verified foundation

The active application is React/Vite served through an asset-serving ESM Worker, with Supabase authentication, database and private document storage. `/check` extracts a supported CV locally, reviews supplied English CV/vacancy wording, permits user edits, requires approval for downloads and offers explicit private saving. The existing workspace provides saved CVs, reorder-only preparation packs and user-reported application stages. Free-check records are immutable approved text snapshots; they are not a structured career master or approved claim graph.

The active app has no production Claude/LLM executor, source-lane search runtime, Gmail triage or draft integration, LinkedIn inbox integration, structured master-record interview, role-variant builder or cross-run verified master apply list. Google authentication is account sign-in, not Gmail authorization. UI previews, old unused modules and research documents do not establish a deployed capability. Relevant current boundaries are `src/pages/CvCheck.tsx`, `src/lib/cv-evidence.ts`, `src/lib/free-check-api.ts`, `src/lib/workspace-api.ts` and the deterministic `groundedTailor` in `supabase/functions/_shared/core.ts`.

## Source behavior that needs a deliberate port

The skills combine instructions, host tools and Python scripts. Copying their markdown into a web page does not reproduce the tool calls. `applied_ledger.py` starts with an empty `LEDGER` that orchestration must fill; `outreach.py` produces text and Gmail payloads but does not itself create drafts. Browser triage, contact research, organization research, interview intake and proposed phrasing are supplied by the host/model or person. The inspected CV Python pipeline does not itself call an LLM for these missing decisions.

The reviewed shared full-loop copy contains neither `engine/loop2/registry_seed.json` nor a live workspace `output/loop2/registry.json`. `sweep.py::load_registry` returns an empty list when both are absent. The presence of source adapters therefore does not establish a configured employer sweep: the registry must be supplied, owner/market-scoped and each endpoint freshly tested. An empty registry must produce a missing-configuration status, not “the market returned no jobs.” A different local workspace may have its own registry; that was not inspected or assumed.

The full-loop prose maps role fit from a 55–95 diagnostic band; `run_loop2.py::job_match` actually uses a 60–90 band: `clamp(round((best_ats−60)/30×40), 0, 40)`. Its compensation estimate also includes title/company heuristics. These are compatibility details and biases, not objective salary evidence. Pin the reviewed engine and document the implemented formula rather than claiming exact parity with inconsistent prose.

Claim safeguards are useful but narrower than “verified truth.” `cvlib.py::phrasing_render` rejects unconfirmed/third-party achievements and unreleased/withdrawn figures without a clean safe phrasing. `make_claims.py` preserves achievement/phrasing IDs, source category and era; it does not by itself provide precise uploaded-document quote offsets or independently validate what the user said. Regex/name/number purges cannot establish semantic truth or prevent every attribution error. Keep those guards and add precise source references, claim versioning, meaning review and explicit user approval.

## Adapting to the actual audience

The core is shared: profile-driven targets; confirmed owned claims; honest disclosures; surgical variants; sourced roles and contacts; visible unknowns; application continuity; human-approved materials; draft-only boundaries. Senior strategy preferences are a template, not the product's identity.

| Audience | Genuine records and targets | Required adaptation |
| --- | --- | --- |
| Student | Education status, coursework/projects, internships, part-time work, volunteering, demonstrable tools and graduate-program dates. | Include internship/graduate/trainee/analyst titles. Distinguish an academic case study from employment/client delivery. Preserve expected vs awarded degree status. A useful non-numeric project is allowed; never manufacture business impact. One-page output can be appropriate. |
| MBA applicant | Prior work, current program, projects, internships, recruiting windows, target functions and preferred markets. | Treat MBA enrollment and graduation timing accurately. Support consulting, finance, product, operations and other selected families only where the record supports them. Alumni paths must be supplied or sourced, never guessed. |
| Busy career switcher | Existing achievements, transferable scope, target role families, constraints, discretion and explicit gaps. | Re-angle facts without promoting support into leadership or creating hands-on expertise. Reuse the approved record; prioritize replies/deadlines, carried roles and the correct submitted version. Current-employer confidentiality remains an explicit control. |

Actual code currently prevents profile-only adaptation. `engine/loop2/titles.py` extends profile families and levels but its hard `EXCLUDE` still contains intern, internship, graduate, trainee, product manager, accounting/FP&A and many other potential target roles. Its built-in senior level/family filters and UAE market defaults also remain active. `run_loop2.py` and outreach have senior family fallbacks; changing just the homepage or `target_titles` is insufficient.

Make level/family inclusion and exclusions validated per-profile configuration with no inherited senior exclusions. Remove automatic market/nationality assumptions until the user selects and confirms relevant eligibility information. An optional contractual hold is set only from that user's circumstances; do not inherit someone else's counsel gate. Pay can be annual, monthly, hourly or stipend-based with an explicit basis, and unknown pay remains unknown.

The source requires metrics in a large share of bullets; `make_claims.py` also requires a metric for an automatically insertable claim. Those defaults can discard honest early-career evidence. Permit approved, source-backed non-numeric achievements and change the style template rather than inventing numbers. Similarly, 5–6 variants, a long master document, two pages and senior writing conventions should be candidate-configured output choices. Changes from exact source defaults must be labeled and tested; factual and disclosure gates stay intact.

## Minimum architecture that preserves the runtime

The local-versus-cloud choice is pending. Both options need the same versioned contract and must expose which stages actually ran. A bounded assisted run is preferable to advertising an autonomous loop that lacks its integrations.

### Common contract

Persist candidate/profile versions, source passages, approved claim/phrasing versions, role-family configurations, opportunity snapshots, run/source-lane logs, assessments, application artifact manifests, contact evidence, draft states, application events and next actions. Each record is owner-scoped. A run records input hashes, engine/config version, source verification times and per-stage success/failure. Job descriptions, messages and model output are untrusted data; they cannot authorize tools or edits.

Use the existing web app for intake, source/claim confirmation, target configuration, run review, explicit draft approval and artifact access. Keep the present free check as the entry/source-review component. Extend the workspace around opportunities and runs; do not rename the existing checker “job-loop” until the corresponding stages exist.

### Option A: local Claude-first bridge

Run a pinned, reviewed engine in the person's own configured workspace, with its Python dependencies (`python-docx`, `pypdf`, HTTP/HTML parsing libraries, and Windows Word automation support where used), a populated source registry and Word/private instance or LibreOffice renderer. The host provides its own available research/mail/browser tools; missing tools are reported. Start with user-triggered runs and import a structured run manifest plus approved artifacts into Jobvance. A paired local bridge is a later transport option; it must accept a fixed operation/schema, not arbitrary markdown commands from the browser.

This most closely retains the original operating model, but requires local setup and an active permitted host session. It is not an install-free cloud product and cannot promise full operation for users without that runtime. Do not upload a mailbox, local browser cookies or a whole personal workspace merely to display a report.

### Option B: standalone cloud port

Keep the static Worker/frontend and Supabase identity/storage. Add an authenticated job-control API and durable queued run state. Execute reviewed Python stages in an isolated process/container per owner/run with a pinned renderer, installed dependencies, controlled filesystem and bounded resource/network access. Module-global profile imports and shared filenames must not bleed across users; a fresh isolated process and artifact manifest provide the boundary.

Add a constrained production model/orchestration runtime for the steps the scripts do not perform. An operated Claude Agent SDK process is one option; direct API calls with an explicitly written tool loop are another. Anthropic distinguishes these approaches and states that third-party products cannot offer consumer Claude login/rate limits without prior approval; API authentication is the documented route. [Official Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview).

Register narrow tools for approved-claim selection, safe role-source fetching, contact evidence, render validation and report assembly. Do not register email sending, applying, arbitrary shell or general account-control tools. Model edits are proposed structured changes, not automatically accepted career facts. A safe fetcher checks HTTPS destinations, private/internal addresses, redirects, size/time limits and allowed source adapters. Cached postings and artifacts retain freshness/version metadata.

The current Worker has no configured Python/document conversion process or agent bindings; current Supabase functions do not supply the missing orchestration. This port needs deployed services and connector credentials, not only frontend screens. No service, API account or paid runtime has been provisioned by this document.

### Integrations that cannot be assumed

Gmail reading and ordinary draft management require separate consent/scopes and the applicable provider review. Google's scope table classifies `gmail.readonly` and `gmail.compose` as restricted, and compose also permits sending. A draft-only promise therefore needs code/tool/transport enforcement in addition to OAuth selection. An add-on scoped to the currently opened message cannot reproduce a month-long mailbox ledger. [Official Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes).

LinkedIn's agreement restricts scraping/copying and unauthorized automated access. Existing personal browser instructions are not a public SaaS permission grant. Use a supported permitted route or an explicit user-supplied/manual source path, and identify that as a parity limitation. Do not bypass access controls, claim a privileged jobs/messaging API or promise that a guest result is verified. [LinkedIn User Agreement, section 8](https://www.linkedin.com/legal/user-agreement).

Employer adapters require their own fresh tests and source permission assessment; the source's historical registry is not current proof of availability. Platform-blocked lanes can remain manual/unavailable with visible logs. A fully automated three-lane claim is unavailable while these dependencies remain unresolved.

## Acceptance gates before calling the product a loop

1. **Audience gate:** fictional student, MBA and career-switcher profiles retain their intended target roles; graduate/intern/product/finance fixtures cannot be silently excluded by senior defaults. Missing eligibility/pay data yields unknown, not an invented conclusion.
2. **Record gate:** import/interview → confirm → variants → correction/withdrawal is demonstrated. Unconfirmed credentials, a confidential metric, a third-party case-study result and a support-to-lead rewrite cannot reach a newly approved export. Each permitted claim opens its source.
3. **Research gate:** run permitted source lanes with reproducible logs, full JD snapshots and fresh verification. A failed/blocked lane produces an incomplete-run warning; a thin real result is delivered without filler. Manual imports are explicitly marked manual.
4. **Continuity gate:** dedupe the same requisition across routes, retain distinct same-title roles, replay an applied receipt safely, keep ambiguous receipts uncertain, and carry over an open unsubmitted role while excluding a confirmed applied/closed role.
5. **Preparation gate:** each qualifying full-loop role receives its own build attempt and manifest. PDFs are actually rendered and inspected; stale PDF, wrong family, unsupported fact or failed page/style check is visible and cannot be presented as ready. Source-compatible diagnostics show real values and their limits.
6. **Action gate:** action-needed replies/deadlines lead the report. A verified named contact gets a grounded preview; missing/uncertain contact or held employer gets a research task instead. Explicit draft approval is necessary, existing-thread context is preserved, and no send/apply operation can run.
7. **Runtime gate:** retry/cancel/restart, per-user isolation, input/config hashes, quotas, bounded source/model/render work and auditable partial failures are tested. One run cannot overwrite another person's profile or reuse their artifact.

These are functional acceptance tests, not promises of interviews or employment. Keep the beta free; this task introduces no payments, ads, outreach or live integrations. The first release that can honestly be called a loop should complete a bounded opportunity-and-action cycle for one of the target profiles, with the original preparation safeguards and every unavailable step plainly reported.
