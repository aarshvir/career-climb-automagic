# Administration and router security review

12 October 2026. Local adversarial review of the working tree, limited to practical P0/P1 defects. The reviewed scope includes the new administration/review/router/config modules, three `20261012` migrations, administration frontend/API/routes, and candidate processing-route changes. This is independent of the Kimi/Muse product reviews and does not modify their baseline, prompts or scores.

**Verdict: no outstanding P0/P1 findings in the reviewed source.** One reproduced P1 availability regression was corrected by the implementation owner and independently reverified before the review closed. No practical P0/P1 unauthorized access, consent bypass, credential disclosure or budget bypass was found.

## Finding

**[P1, resolved] The new processing-route boundary rejected every manual browser preparation run.**

Before correction, `supabase/functions/_shared/job-loop-engine.ts:146` added `processingRoute` to the `start_run` key list and `:150` required every listed field. Existing rules-only browser requests omit the field (`src/pages/JobLoop.tsx:271`), while `job-loop-engine.ts:160` rejects an actual external route when the provider is `rules`. Separately, `src/lib/job-loop-api.ts:68` omitted `processingRoute` from its Zod action schema, and `:116` parsed/stripped it before invocation. Its model snapshot schema at `:46` also stripped `transport`, causing a browser OpenRouter selection to be treated as direct.

**Observed locally:** invoking the real `validateAction` with a synthetic rules request returned `An action is missing required inputs`; adding `processingRoute: 'direct'` returned `Rules preparation does not authorize an external processing route`. No service or model call occurred. The server route checks fail closed, so this finding is availability rather than private-data disclosure.

**Correction independently verified:** `job-loop-engine.ts:150` now excludes `processingRoute` from required-key checks, while `:160` retains route validation and rules-route rejection. `src/lib/job-loop-api.ts:46,68` now preserves validated model `transport` and action `processingRoute`. Three added regressions at `src/__tests__/lib/job-loop-api.test.ts:18–30` pass the real server validator the browser-serialized OpenRouter/rules body and verify parsed model transport. The 26 API tests plus 18 engine tests passed. A separate local validator invocation accepted rules without a route, paid legacy direct without a route, and paid explicit OpenRouter; it still rejected rules with a direct route. No hosted candidate function was invoked by this review.

## Security controls examined

| Boundary | Evidence and assessment |
| --- | --- |
| Identity and fresh membership | `jobvance-admin.ts:52–60` uses server `auth.getUser(token)` and an active UUID membership lookup on every request. Database RPCs recheck membership under a share lock (`20261012180814_jobvance_admin_platform.sql:76–82`). The seed at `:11–14` binds one existing UUID; no signup grant or user-metadata authorization appears in this migration. |
| Owner/operator separation and private RPCs | Owner-only configuration is enforced in HTTP (`jobvance-admin.ts:74–76`) and SQL (`20261012180814_jobvance_admin_platform.sql:156`). Paid review reservations require owner membership (`20261012183431_jobvance_admin_request_identity.sql:11`). Tables enable/force RLS and revoke public/browser privileges (`20261012180814_jobvance_admin_platform.sql:62–74`); privileged functions revoke default execution (`:184–185`, request-identity migration `:59–60`). |
| Selected support-message scope | Snapshots select only receipt metadata (`20261012181402_jobvance_admin_snapshot.sql:41–43`) and minimal account/run fields (`:33–46`). A separate exact-ID RPC returns at most 2,000 characters after active membership verification and audits only receipt/version metadata (`20261012183431_jobvance_admin_request_identity.sql:48–56`). The UI displays the text as React content and clears it on close (`AdminOperations.tsx:15–28`); no model call occurs in this action. |
| One-use tickets | Ticket rows constrain action, payload size and two-minute expiry (`20261012180814_jobvance_admin_platform.sql:39–45`), additionally bound to wall-clock creation (`20261012181402_jobvance_admin_snapshot.sql:3–5`). Atomic consumption requires matching action, unexpired time and unconsumed state, then checks owner/operator authority (`20261012180814_jobvance_admin_platform.sql:84–92`). HTTP cannot supply the stored model payload (`jobvance-review-runtime.ts:121–128,161–169`). |
| Request conflicts and replays | Global unique request identity and request advisory locking precede reservation; all saved call parameters must match (`20261012183431_jobvance_admin_request_identity.sql:5,13–20`). Evidence/action/model/persona/effort bind to the canonical operation hash (`jobvance-review-runtime.ts:169–181`). Replays return a bounded, revalidated result without another external call (`:130–156,183`). |
| Shared $50 ledger and $5 batch ceiling | Candidate and admin reservations use the identical UTC-month budget row lock (`20261012181402_jobvance_admin_snapshot.sql:119–125`; `20261012183431_jobvance_admin_request_identity.sql:27–37`). Batch advisory locking spans month boundaries (`:22–33`). Unknown costs retain full reservations; settlement locks usage and only releases the known difference (`20261012180814_jobvance_admin_platform.sql:138–148`; candidate runtime `job-loop-runtime.ts:174–178`). No blind external retry is added. |
| Candidate consent | Before creating a paid run and before each model call, the configured route must match the candidate's saved route (`job-loop-runtime.ts:137–138,248`). Owner router enablement cannot change an old direct opt-in into an OpenRouter opt-in. The resolved P1 finding above prevented valid browser requests and did not bypass these checks. |
| Deterministic figures and safe model output | SQL computes percentages/zero-denominator handling (`20261012181402_jobvance_admin_snapshot.sql:7–12`); review scores must be unique bounded integers, with the mean computed locally (`jobvance-review-runtime.ts:90–100`). Commentary accepts aggregate input only (`:65–75`) and validates cited metric keys (`:103–106`). Candidate assessments remain deterministic (`job-loop-engine.ts:206–226`). |
| Credential and raw-output handling | The OpenRouter key is read only into server request headers (`jobvance-openrouter.ts:27–30,41–53`). Status/error responses are sanitized (`:31–37,59–70`). Provider reasoning/raw error payloads are excluded; invalid reviews persist only bounded failure codes (`jobvance-review-runtime.ts:190–199`). This is a bounded code-path review, not a claim that all historical repository content was secret-scanned. |

## Verification and limits

- **75 tests passed in five focused suites:** admin migration, review runtime, admin API, ticket runner and administration UI journeys. The SQL suite applies all three new migrations to a disposable synthetic PGlite database, including browser-role denial, revocation, selected support access, request conflicts, cap checks, unknown-cost retention and deterministic metrics.
- **63 tests passed in six backend suites:** administration, OpenRouter, candidate engine, replay, processing and scheduling. Existing suites passed despite the reproduced manual-run defect; their mocks/local assertions did not cover the complete browser-parser/server-validator boundary.
- **44 tests passed during correction verification:** 26 candidate API tests and 18 engine tests, including the three new regressions. These executions overlap the earlier engine suite and should not be counted as 44 additional unique tests.
- Isolated test temporary files used `.sites-runtime/security-test-temp`. No live secret, private customer record, account mutation, live database query, paid generation, deployment or commit was performed. The only review artifact written is this document.
- PGlite serializes work through one embedded connection. Promise-based fixture tests and static lock analysis support the reservation design, but do not demonstrate real multi-session Postgres contention or UTC rollover under load. Actual hosted RLS grants, applied migrations, gateway behavior and authenticated production journeys remain unverified by this review.
- Current official [Supabase getUser documentation](https://supabase.com/docs/reference/javascript/auth-getuser) and [RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) were consulted. The Markdown changelog endpoint could not be fetched by the browser tool. No implementation was changed based on those documents.
