## Findings and recommendations

**DB-01 — P1: make erasure an enduring database state.** Observed in an isolated SQL fixture, not production. `20261011030000_job_loop_recurring.sql:233–240` deactivates the pilot and cancels/revokes existing work. Yet `:36–51` immediately allows a new run to reactivate that same account; the storage guard at `:247–256` accepts it once active again. The repository scans the object prefix, then deletes the collected objects, then finishes erasure (`job-loop-repository.ts:75–88`). A second session can start work and upload after that scan but before finish. `finish_erase` deletes database authority, not storage objects (`recurring.sql:257–269`). My fixture leaves zero records/runs and one private storage object. This is a private orphan-retention gap; it does not demonstrate public or cross-tenant exposure, and the bucket remains private.

Add a durable `erasing` generation/tombstone checked by record writes, enrollment, schedules, run creation, OAuth activation and storage insertion. Keep the fence until storage deletion and a final empty-prefix check succeed; allow deliberate fresh enrollment only after completion. Make retry progress durable. Acceptance: interleave erase/start/upload in two sessions and ensure the latter two fail; interrupt each deletion stage and retry to an empty prefix, no records, inactive seat, and unchanged committed spending. Dependencies: database/API/storage changes and concurrency fixture; **2–4 engineer-days**, required before widening the pilot.

Reproduce from repository root: `node .tmp/20-role-review/03-database-architect/erase-interleave.mjs`. The fixture asserts reactivation, then `records=0`, `runs=0`, `storage_objects_left=1`, and private bucket status. It runs entirely in memory against the first three Loop migrations; this scenario's functions are not changed by the subsequent dispatch/lease migrations. The existing erasure test only exercises a sequential happy path (`supabase/tests/job-loop-recurring-sql.test.ts:85–88`).

**DB-02 — P2: use one lock order for editor and worker transactions.** Source-confirmed inversion; an actual deadlock was not observed. The current record-write function locks the record and then updates active runs (`recurring.sql:168–175`), while phase commit locks the run and then the record (`job_loop_cloud.sql:137–140`). Saving a factual correction while a phase commits can therefore form a wait cycle. PostgreSQL aborting one transaction preserves integrity but can surface a retry/error during a core workflow. Choose one ordering, preferably the account/record serialization point before child runs, across write/start/commit/erase/approval. Acceptance: a real PostgreSQL two-connection test repeatedly overlaps correction and commit, observes no `40P01`, and still rejects stale publication. Dependencies: database function review and multi-connection test environment; **1–2 days**. Reasonable pilot work; no measured incident is claimed.

**DB-03 — P2: separate list metadata from document bodies.** `job-loop-repository.ts:44–51` fetches `*` for 30 runs and 150 packets even though `publicRun` discards the run snapshot (`:105–107`); each refresh assembles these collections (`job-loop-runtime.ts:61–65`). Source limits permit 2 MB snapshots/data and 1 MB packets (`job_loop_cloud.sql:21–22,33`). This establishes avoidable payload amplification, not observed slow performance. Fetch run summaries, paginate packet summaries and retrieve full document/evidence only on selection. Add measured `(user_id,created_at DESC,id)` packet/support and owner/run usage indexes; move recovery's lease filter before its limit (`repository.ts:71–73`). Acceptance: representative ten-user fixtures, `EXPLAIN (ANALYZE, BUFFERS)`, payload measurement, deterministic pagination and exact selected-document parity. Dependencies: snapshot/UI contract changes; **1–3 days**. Do not introduce sharding, vector storage or a separate queue service for this pilot.

**DB-04 — P2: make signed-in support intake atomic and retryable.** Guest support already uses a unique request ID, atomic advisory-lock quota, hashed bearer receipt, bounded messages and service-only access (`20261014020000_jobvance_guest_support.sql:21–53,92–101`). Signed-in support instead counts recent rows and inserts separately, with no request key (`job-loop-runtime.ts:80–84`; recurring migration:26). Concurrent submissions can bypass five/day and an ambiguous retry can create duplicates. Reuse the guest intake pattern in one authenticated RPC with owner/request uniqueness and an atomic quota. Acceptance: ten parallel submissions admit five, replaying one request creates one row, changed payload conflicts, foreign owners cannot read it. Dependencies: control contract and support migration; **0.5–1.5 days**, pilot iteration rather than launch-blocking security work.
