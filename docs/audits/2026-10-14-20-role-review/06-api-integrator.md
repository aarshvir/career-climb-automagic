**API-01 — P1: retain the actual processing route in historical receipts.** The server saves route consent (`job-loop-runtime.ts:139`), but `publicRun` omits it (`job-loop-repository.ts:107`). The history UI obtains a label from today's `snapshot.models` (`JobLoop.tsx:365`). A configuration change can therefore relabel an older direct run as “via OpenRouter,” or the reverse. Router canonical model/request ID are returned internally (`jobvance-openrouter.ts:71`) but dropped by the loop adapter. Preserve actual transport, canonical model and safe provider request reference with settlement; display historical records from that receipt. Accept when direct→router→direct switches leave all earlier labels unchanged and uncertain attempts remain distinct. Dependencies: shared run/result schema and compatible old-record fallback. **1–2 days; no new service cost; required before widening model use.**

**API-02 — P1: close the email-auth acceptance gap before inviting more users.** Email signup and reset are real product operations (`AuthContext.tsx:100–121`), yet this review has no confirmation that an ordinary non-team pilot address receives confirmation/recovery mail. Account counts do not establish delivery. This is an evidence gap, not an observed outage. Current [Supabase SMTP documentation](https://supabase.com/docs/guides/auth/auth-smtp), checked14 October2026, says its default mail service is restricted to project-team addresses and currently two messages/hour. Have the owner record current email-confirmation, allowed redirect and SMTP state without copying secrets. Reuse an existing SMTP account if needed; configure sender domain and host/port/user/password in Supabase Auth, then later authorize one real invited-address confirmation/reset acceptance check. Accept valid/expired links, correct return destination and recovery of the original private account. **0.5–1.5 days plus domain/operator access; vendor cost unverified, separately budgeted; do not add Auth0 or SMS authentication.**

**API-03 — P2: reconcile operator instructions with actual limits and configuration authority.** `CLOUD-JOB-LOOP-ACCOUNTS.md:61,80,82` describes three queries, five preparations and scheduling as later; current `LIMITS` is two queries/two packets, while scheduler readiness is runtime-reported. The guide's old cost illustration overstates current work per run. Document direct-provider enablement separately from the owner-controlled OpenRouter setting, which `configuredLoopEnv` resolves from private admin configuration rather than merely trusting an environment toggle. Keep current model/price eligibility as a dated check: a valid key alone explicitly does not prove a supported funded route. Accept one authoritative setup matrix matching runtime snapshots and quoted limits. **0.5–1 day; no account purchase; pilot required.**

**API-04 — P2: make Gmail reconnection state explicit before enabling it.** Encryption, PKCE, one-use owner-bound activation, explicit mailbox confirmation, attachment hashes and uncertain-draft replay blocking are strong. However snapshot “connected” means a stored row (`job-loop-runtime.ts:64–65`); token failures become a generic read error and do not persist “reauthorization required” (`gmail.ts:38–40,74–85`). A revoked/expired connection could continue appearing connected; this was not reproduced live. Distinguish transient429/5xx from revoked/invalid grants, persist the latter, expose reconnect and never retry draft writes. Google confirms restricted [read/compose scopes and server-data assessment requirements](https://developers.google.com/workspace/gmail/api/auth/scopes); external Testing refresh tokens [expire after seven days](https://developers.google.com/identity/protocols/oauth2#expiration). Accept revoke, expiry, tester-day-eight and ambiguous-draft cases. **1–2 days plus Google project/Web OAuth/consent configuration; optional, not needed for this pilot.**
