## Findings and actions

**SEC-01 — P1: Require stronger sessions for administrators. Source-confirmed hardening gap; compromise is hypothetical.** `supabase/functions/_shared/jobvance-admin.ts:55–64` accepts any valid bearer session whose user has an active owner/operator row. The authenticated user contract contains only an ID; neither assurance level nor a recent step-up is required. `supabase/migrations/20261012180814_jobvance_admin_platform.sql:77–82` correctly rechecks membership, but does not add session assurance. Existing tests explicitly accept a fixture with only an ID (`supabase/tests/jobvance-admin.test.ts:13–23`). This is not an outsider privilege bypass: it increases the consequence of a stolen administrator session, particularly private support reads and global scheduler/model settings.

Add verified MFA assurance and recent reauthentication for sensitive administration operations, with a clear recovery process and individually assigned administrator accounts. Do not trust editable metadata or an unverified decoded token to establish assurance. Verify that a current member with a lower-assurance session cannot read support detail or change settings, an appropriately stepped-up member can, and role revocation still takes effect. Dependency: chosen identity-provider MFA/recovery configuration; production enrollment is unverified here. Planning estimate: **1–3 engineering days**, plus owner enrollment; small operational cost, no model/search cost. This should precede widening the pilot.

**SEC-02 — P2: Give PDF extraction a cumulative budget and cancellation. Source-confirmed missing bound; exhaustion is unproven.** `src/lib/cv-extraction.ts:51–74` limits compressed input to 5 MB and documents to 100 pages, then collects all text before the 60,000-character validation. It supplies no application deadline or cancellation signal. A compact, unusually complex PDF can therefore consume substantially more work than its compressed size suggests, or keep a user's browser busy after they abandon extraction. No malicious file was executed and no crash is claimed. DOCX already provides a useful precedent: `src/lib/cv-docx.ts:14–46` checks advertised and actual inflated XML bytes and processes small compressed chunks.

Track cumulative text and page work while extracting, reject immediately when the CV text budget is exceeded, and expose cancel/timeout that destroys the PDF task and discards stale results. Use synthetic, non-destructive fixtures and a deliberately slow mocked task to verify cancellation, early rejection and successful subsequent upload. Dependency: extraction UI state and PDF worker lifecycle. Estimate: **0.5–1.5 days**; negligible recurring cost. Useful during the current pilot, especially on student/mobile hardware.

**SEC-03 — P2: Prove the guest-support rate identity at the actual ingress. Source-confirmed trust assumption; bypass is a hypothesis.** `supabase/functions/jobvance-guest-support/index.ts:11` prefers `cf-connecting-ip`, then the first `x-forwarded-for` entry, to calculate an HMAC rate key. The SQL applies five requests/hour per key and 100/day globally (`supabase/migrations/20261014020000_jobvance_guest_support.sql:37–39`). Hashing protects the retained address but does not establish that a header came from a trusted proxy. I did not verify whether the deployed ingress strips/overwrites these headers. If it does not, a caller can vary the apparent identity, consume the shared daily allowance and deny legitimate support intake. Even genuine distributed traffic can exhaust that intentionally small global cap.

Document the trusted ingress contract, derive identity exclusively from an ingress-controlled value, and test through a staging deployment using fictional requests and spoofed-header variations. Add inexpensive edge throttling and observable aggregate rejection counts; keep the SQL cap as a backstop and preserve drafts on rejection. Verify equal canonical clients receive the same quota regardless of supplied headers and blocked creates do not affect existing receipt reads. Dependencies: hosting/edge header behavior and staging access. Estimate: **0.5–2 days**; usually negligible pilot cost. Do not raise the global cap before this test.

## Verified strengths and limits

Two bounded runs passed **124 tests across nine files**, with `--maxWorkers=4`: the backend run covered admin authorization, guest schemas/hashing/SQL access, scheduler ticket replay, cloud SQL ownership and Paddle signatures; the frontend run covered extraction, hosted model consent and private download handling. Exact commands are recorded in the JSON. These include real local PostgreSQL fixtures, not proof of deployed grants.

Guest receipts use 32 random bytes, retain only a bearer hash server-side, and stay out of URLs/local storage (`src/lib/guest-support.ts:7–9`, `src/pages/GuestSupport.tsx:17`). Server logging emits error types, while audit details are allowlisted rather than raw CV/provider text. Model payloads contain explicitly eligible claims and vacancy text; fixed endpoints and redirect rejection reduce SSRF opportunities. No arbitrary SQL string construction or raw HTML rendering of candidate text was identified in examined current flows. Paddle authenticates raw bodies and rejects stale signatures; billing remains disabled under the brief's bounds.

Order the work: privileged-session gate, staging ingress/tenant-boundary verification, then extraction cancellation. Revalidate deployed RLS, signed-link expiry/revocation behavior, scheduler grants and retention-job execution using fictional isolated accounts before expansion. Issued 120-second links are bearer capabilities; immediate revocation after issuance was not established. Do not build custom cryptography, a full security platform, broad file-type support or paid scanning infrastructure for this ten-user pilot.
