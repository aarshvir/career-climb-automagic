# Recurring Job Loop billing: edge implementation and integration review

18 October 2026. This is a bounded implementation and independent source review from a separate agent context. It is not proof of a real charge, provider renewal, delivered customer service or a general commercial sign-off.

## Delivered edge contract

`job-loop-billing` is an authenticated POST endpoint. `status` is passive. `checkout` requires an immutable request UUID, listed monthly plan, displayed lifecycle generation and explicit purchase consent. `cancel` requires the original request UUID, current displayed generation, exact subscription ID/revision and explicit cancellation consent. The owner comes from `auth.getUser`, the actual session ID comes from that verified bearer token, and SQL checks its continuing `auth.sessions` authority.

The public plan IDs are `weekly`, `active` and `daily`, priced at tax-inclusive USD 29/59/99 each month. `active` maps to the existing server cadence `three_weekly`. All three permit three CV variants. Checkout never silently adds a trial. Products are read and checked against fixed currency, monthly frequency, twenty-year renewable product term, no trial/discount/PPP and tax-inclusive settings before checkout creation. The term is the provider's configured maximum duration; charges remain monthly until cancellation.

Configuration uses `JOBVANCE_LOOP_BILLING_ENABLED=true`, `DODO_PRODUCT_LOOP_WEEKLY`, `DODO_PRODUCT_LOOP_ACTIVE` and `DODO_PRODUCT_LOOP_DAILY`, plus all existing Dodo live merchant/legal/support/key/origin gates. The securely saved singular `DODO_PAYMENT_API_KEY` is accepted only if the canonical `DODO_PAYMENTS_API_KEY` is absent or identical. Different nonempty values disable Dodo configuration. No secret is returned or logged.

`dodo-webhook` verifies the exact raw body before recurring routing. A stable signed occurrence fingerprint covers event type/time, payload type, immutable subject/payment/refund/customer IDs and immutable Job Loop metadata. Dodo's delivery snapshots can change status or dates on retries; those mutable changes do not produce a second grant. Conflicting immutable occurrence identities fail closed.

Every new grant requires a provider-read succeeded payment with its immutable `service_periods`. A checkout's provider read must name the initial payment, which must name the exact bound subscription/customer. Static-link metadata alone cannot establish an order. Payment total must equal the fixed tax-inclusive plan amount, with valid tax bounds, customer and subscription identities. Subscription billing dates alone never extend access. A success/renewal event whose payment API is still processing remains retryable and unprocessed. Refunds use the authenticated signed refund plus a provider-read payment and revoke its exact subscription authority; no Refunds API scope is requested.

Cancellation writes only `cancel_at_next_billing_date=true`, then independently reads the subscription. An ambiguous outcome retains its original durable request and is reconciled by reads; it is never blindly posted again. Billing cancellation remains possible after career-data erasure, using the current cancellation intent and the original owned subscription. A verified paid period is preserved. Exact signed `past_due_ends_at` from any supported matching past-due Subscription snapshot supplies grace; delivery time and future billing dates do not create grace.

Deploy together with the service-only SQL migration: `job-loop-billing`, `dodo-webhook`, `create-checkout`, and `get-entitlement`. The latter two need the shared secure-key alias consistently. This agent performed no production configuration, migration, deployment, payment or external provider call.

## Independent integration findings and corrections

1. The frontend originally retained checked purchase/cancellation consent across a billing refresh that changed generation or subscription identity. A customer could confirm cancellation for one subscription and bind a newly displayed subscription. The UI agent corrected this with synchronous consent fingerprints, revocation on every refresh, guarded mutation scope and a refresh sequence that rejects older delayed reads. Three focused regressions cover subscription replacement, generation replacement and out-of-order refresh.
2. SQL originally discarded all stale non-refund events before recording a payment service period. A later subscription update arriving before an older genuine renewal event could therefore lose paid access. The SQL agent corrected this: late immutable payment evidence is stored while newer lifecycle state, cancellation and grace remain authoritative. Correct regressions cover that ordering and same-second paid recovery.
3. Separate reviewers found missing recurring payload-type checks and a product tax setting that could contradict the displayed included-tax price. Both were corrected before final verification. Subscription/payment/refund events require their exact payload types; missing/wrong kinds cannot query the provider or grant access. Monthly products and subscriptions must report tax-inclusive pricing. The actual succeeded total remains the fixed price authority even if the provider's pre-tax subscription amount is lower because tax is included.
4. Review retained explicit current effective entitlement in the UI instead of inferring access from a subscription's maximum recorded end date. Paid-but-unfulfilled capacity cases expose `fulfillmentPending` and block another purchase. Recovery carries the original cancellation request without restoring consent or automatically retrying.

## Final bounded verification

The final targeted run passed **323 tests across 11 files** covering the new edge orchestration, actual edge entrypoints with hermetic SDK/provider HTTP adapters, integrated real SQL in PGlite, client/UI recovery and authority, recurrence entitlement guards, and existing Dodo/core/pass regression paths. Four deployed-source entrypoints passed Deno checking: Job Loop billing, Dodo webhook, create checkout and get entitlement.

The SQL journey invokes the actual edge orchestration through real integrated migration routines for initial checkout/payment, renewal, status and cancellation, with isolated provider responses. Native PostgreSQL race evidence and all production deployment/merchant acceptance evidence belong to the release coordinator's separate receipts. No real card, charge, renewal, refund, customer CV, customer erasure or paid AI/search call was used by this agent.
