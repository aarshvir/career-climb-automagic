# Job Loop product reset and repeated-application acceptance

17 October 2026 (Asia/Dubai). The owner explicitly authorized implementation and multiple agents after the v31 no-code-change release. Job Loop is the main recurring product; CV Check is a secondary acquisition route. This assessment does not declare the whole product perfected.

## Implemented

Home and the Job Loop overview now explain the same three stages: add or build your CV; choose jobs, locations and frequency; receive jobs and prepared CVs in the dashboard. The dashboard uses the same ordered, actionable stages, with honest loaded counts and readiness. Desktop panels run left to right and mobile panels stack in the same order. CV Check remains available without being the primary product entry.

A guided builder creates a local CV draft from exact answers, including education/projects for someone with no existing CV. It adds no invented facts and makes no model call. Preview, explicit replacement, exact undo, separate private saving and subsequent fact confirmation remain distinct. Answers recover across route navigation within the existing 30-minute page-memory lifetime, bound to the owner, confirmed auth authority and Loop generation. Refresh/closing the tab still clears page memory. Existing source headers are not silently overwritten.

Independent review caught a same-batch stale preview and a negative auth-authority recovery gap; both were corrected with regressions. Combined auth/lifecycle tests also exposed duplicate sibling React keys between the builder and saved-check chooser; the builder now has its own key namespace, preserving removal on auth uncertainty and lifecycle changes. No ownership or approval guard was weakened to make tests pass.

The $29 Weekly / $59 Active / $99 Daily monthly ladder is displayed as a proposal, with one/three/seven weekly search frequencies respectively (Daily means every calendar day). All three propose up to three reusable CV variants and the guided creator. Checkout remains off. A search run is a cycle, not a guaranteed number of jobs or interviews. See [pricing review](PUBLIC-ENTRY.md) and [backend assessment](backend-capabilities.md).

## Actual bounded acceptance

- The new worker integration runs two distinct selected vacancies through actual worker phases, composition, document rendering, control approval and download checks. The second run preserves the first packet and unchanged retries reuse the existing exact packet.
- A separate actual discovery-worker test uses intercepted Greenhouse HTTP responses to accept a Dubai match, reject a London mismatch, render a PDF and reuse the existing opportunity on the following cycle.
- The real JobLoop page was exercised in desktop and 390×844 mobile IAB views against isolated account/backend adapters. Each of two vacancies was deliberately selected, prepared, previewed and separately approved. Six actual browser downloads were received: PDF, DOCX and TXT for each job. All six were parsed, matched the worker-generated artifact hashes, contained the expected candidate text, and excluded the vacancy-only sentinel. Both PDFs had one page. [Exact receipt](browser-downloads.json).
- The browser harness replays bytes produced by the actual worker test; the preparation button does not invoke a hosted worker. Auth, persistence, approval storage and download URLs are isolated adapters. This proves local UI delivery of real generated bytes, not production auth/Storage, live scheduled dispatch, paid AI quality or unassisted customer success.
- A mobile builder walkthrough used education/project answers, previewed them unchanged, required deliberate source replacement and restored the exact prior CV with undo. No private save or model call occurred.
- Public home, pricing and overview were inspected on desktop/mobile. At desktop width, the three panel positions were x=40/443/846 at the same y; mobile overview positions were x=18 with increasing y and width339. Mobile document width375 at viewport390 showed no horizontal overflow. Test tabs were closed and viewport reset.

## 100-customer simulation

This is an executable matrix of ten career contexts × ten constraints, not 100 actual participants or unassisted sessions. [Results](customer-simulation.md), [individual cases](customer-simulation.json).

The initial matrix produced 50 review-ready cases; 20 correct privacy/confirmation holds; 10 empty-source blocks; 10 missing-search-target gaps; and 10 Chinese-PDF limitations with working DOCX/TXT. Ten additional cases then verified the new builder supplies a usable source for each career context. The protected holds are intentional. Passing assertions about a known limitation do not mean that limitation was fixed. No score uplift or 100% customer success is claimed.

## Still required for the complete commercial product

1. Persist up to three owned CV variants with exact revisions/claim membership and immutable schedule/run selection, preserving historical documents.
2. Add three chosen weekdays and enforced plan entitlements, including 31-day daily months, missed runs, retries, pause/cancellation and no-result behavior.
3. Add explicit recurring AI processing consent and source-bound tailored proposals. Existing recurring runs remain rules-based; manual AI selection does not establish unattended semantic rewriting.
4. Expand useful job coverage beyond the configured employer feeds; enforce useful discovery preferences and address unsupported PDF scripts. Preserve honest source failures/no-match outcomes.
5. Verify hosted signup/auth, scheduled dispatch, worker/Storage delivery and first/second unassisted applications with a dedicated synthetic identity; measure effort and usable outputs with real consenting participants.
6. Retain full-route ambiguous-request recovery, older record retrieval/pagination, per-application grouped review and the earlier outstanding reliability/security/product requirements. This frontend slice does not fix every issue identified in Claude's changes.

No production candidate records, migrations, edge handlers, collection configuration, billing settings or paid providers were changed by this slice. Baseline backend remains control16/worker12/tailor1/OAuth5 from v31. Source rollback tag `jobvance-before-loop-product-reset-2026-10-17` and saved v31 preserve frontend rollback; they do not restore database/files.
