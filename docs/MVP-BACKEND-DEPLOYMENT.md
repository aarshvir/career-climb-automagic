# Reviewed deployment requirements for the application-pack MVP

This implementation is prepared and tested locally. It has not been applied to the production database, deployed as edge functions, or used to make a real payment. Production release requires the staged checks below. Preserve existing CV objects, accounts and legacy jobs.

The current owner has no registered entity and has not completed seller licensing/eligibility or payment-provider approval. **Live billing remains disabled.** Paddle is the selected default adapter, with Stripe retained as an optional adapter. Individual seller onboarding and local permission to trade are separate checks; this implementation does not establish either approval or provide a workaround for them. The founder must resolve the appropriate seller permission and actual Paddle merchant approval before enabling live payments.

## Delivered behavior

- One free application pack per account. Credits are authoritative database grants; browser plan names and local storage do not grant access.
- Proposed paid product: **$29 USD before applicable tax for ten packs, valid 30 days from the successful payment event**. This is one payment, not a renewing subscription. No practitioner review, automated submission, universal ATS score or employer outcome promise is included.
- Tailoring runs without an external AI key. It compares English vocabulary and conservatively reorders explicitly marked bullet blocks while retaining every original factual line, section and qualification. Ambiguous multiline blocks remain unchanged. Matched/missing words are explanations, not hiring predictions. Users review the result before approval.
- The `cv-documents` bucket is private, capped at 5 MB and accepts PDF, DOCX and TXT. Reviewed text must contain 80–60,000 characters; job descriptions 80–20,000. The browser extracts text before persistence; the server reads the saved reviewed text. No CV is forwarded to Make, Apify, OpenAI, Paddle or Stripe in the new workflow.
- Each pack request has a UUID and an input fingerprint. Retrying the same request returns its existing pack without a second debit; reusing that UUID for different inputs fails. Pack insertion and credit consumption commit or roll back together, with a per-account row lock.
- Expiring paid grants are consumed before a non-expiring free grant. A refund, including a partial refund, revokes the unused credits associated with that payment intent. Existing packs and credits from other purchases remain intact. A refund tombstone prevents an older/delayed payment-complete event from restoring refunded capacity. Replay never extends expiry.

## Files and API contract

Apply **only** `supabase/migrations/20261010000000_grounded_application_mvp.sql` for this change. Its new tables are `cv_documents`, `application_packs`, `tracked_applications`, `billing_entitlements`, `billing_orders`, `billing_payments`, `billing_credit_grants`, `billing_refund_adjustments` and `billing_payment_events`. Existing profiles, jobs and resume tables are retained. A repeated application fails transactionally rather than dropping or rebuilding customer data. This migration was revised locally for provider/mode binding before any production application; an earlier revision must not be treated as deployed or already applied.

The migration removes browser insert/delete access to `profiles`, removes updates to billing/identity columns, and allows only available self-service columns (`email`, `full_name`, `name`, `avatar_url`). The signup trigger remains able to create profiles under its existing server privileges. New packs are server-inserted; browser updates are restricted to reviewed text/status. Tracking references must belong to the same account. Storage uses restrictive policies to fence older broad policies for the new bucket.

All functions accept POST. `tailor-cv`, `get-entitlement` and `create-checkout` verify the bearer token with `auth.getUser`, derive user identity on the server, and reject invalid sessions before persistence. The privileged database functions are executable only by `service_role`. Their table policies and column grants still protect direct browser access.

`get-entitlement` returns `{creditsRemaining, expiresAt, billingConfigured, billingMode,paymentProvider}`; billing mode is `test`, `live` or null, provider is `paddle`, `stripe` or null. A disabled purchase flow does not turn an existing paid purchase into browser-managed access. `tailor-cv` returns `{pack}`. `create-checkout` accepts only `{requestId}` as authority and returns `{provider:'paddle',transactionId,billingMode}` for Paddle, or `{provider:'stripe',url,sessionId,billingMode}` for Stripe. Client price, quantity, credits and user fields are ignored. New checkout attempts are limited to ten per account in a rolling 24 hours; retries reuse the stored order. Orders bind provider and environment; sandbox paid grants are not counted or consumed in live mode.

Paddle checkout uses the official Paddle.js overlay with the returned transaction ID and a **public client-side token**. It does not manufacture a hosted Paddle checkout URL or redirect users to the transaction's generated payment-link URL. The server first fetches `PADDLE_PRICE_ID` and verifies active status, USD 2,900 cents, one-time billing, no trial, tax-exclusive pricing and no geographic price overrides. It creates one automatic-collection transaction with quantity one and server-owned `custom_data`.

The reviewed Paddle API pages do not document a create-transaction idempotency key. A durable database creation claim therefore allows only one provider creation attempt per request ID. Concurrent calls cannot create two drafts. If the provider call times out or persistence fails ambiguously, a retry does not blindly create another transaction: it requires recovery/reconciliation or a new request. An orphan draft not returned to the browser grants no credit. This limitation is explicit rather than an assertion of distributed exactly-once delivery.

Paddle public tokens can create client-side checkouts with custom data, so a valid signed event alone is insufficient. The webhook also requires a transaction already bound by our authenticated backend to the same user, request, provider and environment. This prevents a client-created transaction or altered custom data from assigning capacity to an arbitrary account.

## Required setup

Use a separate Supabase project and Paddle sandbox for the first integrated run. Keep test payments and grants out of the production project. The backend uses the standard injected `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; these must remain server-only. Never put a service role or payment API secret in a `VITE_*` variable. Only Paddle's public client-side token belongs in the frontend (`VITE_PADDLE_CLIENT_TOKEN`), using a matching sandbox/live token and the primary frontend's explicit payment configuration.

In **Supabase → Edge Functions → Secrets**, configure:

| Name | Staging value / rule |
|---|---|
| `APP_URL` | The root staging URL, e.g. `https://staging.example.com`; no path/query |
| `ALLOWED_ORIGINS` | Comma-separated exact frontend origins; include the intended preview origin |
| `JOBVANCE_BILLING_ENABLED` | `false` initially; switch to `true` only for reviewed payment tests |
| `JOBVANCE_BILLING_MODE` | `test` |
| `JOBVANCE_PAYMENT_PROVIDER` | `paddle` (default); `stripe` only if deliberately selecting the optional adapter |
| `PADDLE_API_KEY` | The Paddle sandbox API key (`pdl_sdbx_apikey_...`), entered privately |
| `PADDLE_PRICE_ID` | Sandbox `pri_...` for the active USD $29 one-time, tax-exclusive price |
| `PADDLE_WEBHOOK_SECRET` | Signing secret of this project's sandbox notification destination, entered privately |
| `JOBVANCE_LIVE_BILLING_REVIEWED` | Absent/false during staging |
| `JOBVANCE_COMMERCIAL_TERMS_REVIEWED` | Absent/false until final live pricing/refund terms have been reviewed |
| `JOBVANCE_SELLER_ELIGIBILITY_REVIEWED` | Absent/false until the owner's actual seller eligibility and local permission to trade have been reviewed |
| `JOBVANCE_PADDLE_MERCHANT_APPROVAL_REVIEWED` | Absent/false until actual Paddle merchant/domain/product approval is confirmed |
| `SUPPORT_EMAIL` | Real monitored merchant support address; must match the published support contact for live billing |

Billing is unavailable unless the enable flag, provider, mode, matching key prefix, signing secret and root URL are valid; Paddle also requires a valid configured price ID. Live mode additionally requires HTTPS, a valid `SUPPORT_EMAIL`, the three review flags for billing, commercial terms and seller eligibility, and Paddle merchant approval when selecting Paddle. These flags are configuration gates, not evidence that any approval exists. The founder must verify the actual permissions, provider approval, published support address and final commercial terms before setting them. No flag has been set by this implementation.

For Paddle, configure `https://<PROJECT_REF>.supabase.co/functions/v1/paddle-webhook` and subscribe to `transaction.completed`, `adjustment.created`, and `adjustment.updated`. Only completed transactions with the expected single line, USD $29 subtotal before tax, quantity and one-time price can grant capacity. Signature validation uses `Paddle-Signature`, `ts:raw-body` HMAC-SHA256, and the documented five-second timestamp tolerance. Refunds require `action=refund,status=approved` and a verified transaction fetched from the selected sandbox/live API. Pending/rejected adjustments do not revoke capacity; approved adjustment IDs are deduplicated separately so created/updated events do not double-count a refund. [Paddle signatures](https://developer.paddle.com/webhooks/about/signature-verification/), [adjustment events](https://developer.paddle.com/webhooks/adjustments/adjustment-updated/).

Create the price and frontend public token in the sandbox account, then verify the overlay with synthetic customer data. API key permissions must cover price reads, transaction creation/reads and the intended notification integration. Configure the checkout domain/default payment-link settings required by the actual account. Overlay implementation does not establish approval of a domain, product or merchant. [Price API](https://developer.paddle.com/api-reference/prices/get-price/), [transaction API](https://developer.paddle.com/api-reference/transactions/create-transaction/), [Paddle.js transaction overlay](https://developer.paddle.com/paddle-js/methods/paddle-checkout-open/).

If deliberately selecting Stripe, privately configure `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` in matching test/live mode and use `https://<PROJECT_REF>.supabase.co/functions/v1/stripe-webhook`. Subscribe to `checkout.session.completed`, `checkout.session.async_payment_succeeded` and `charge.refunded`. The endpoint requires the Stripe signature, not a Supabase JWT. It validates the exact raw body, five-minute tolerance, USD 2,900 cents, product and mode. Refund processing retrieves the intent's server-owned metadata. This optional adapter has the same seller-eligibility and commercial-review gates; selecting it does not resolve the owner's eligibility constraint.

The function configuration deliberately uses in-handler authentication for the new user functions (`verify_jwt=false`) and signature authentication for the webhook. Do not remove the `getUser` checks or replace them with a client-supplied ID. Review the actual project's signing-key and gateway settings during staging. [Supabase authentication documentation](https://supabase.com/docs/guides/functions/auth), [Stripe signature and event documentation](https://docs.stripe.com/events/manage-webhook-endpoints).

## Verification completed here and its limits

The portable core and PGlite suites exercise real PostgreSQL SQL/PLpgSQL for the new migration with an isolated fixture `auth`/`storage` schema. They check ownership, broad-policy fencing, column privilege revocation, signup preservation, transaction rollback, idempotency, credit limits, purchase-specific refunds, replay and out-of-order tombstones. They do not emulate the hosted Storage API's file-byte checks or the real project's unknown policies/triggers.

PGlite serializes a single PostgreSQL connection. Queued simultaneous requests pass the atomic allowance tests, and the production SQL includes account/grant row locks, but this is **not** a multi-connection concurrency/load test. Run an actual two-session staging race before release: two requests against one remaining credit must persist exactly one pack. No production database was used.

The Deno suite runs the actual edge handlers with all fetches intercepted. It proves authentication rejection, owned-CV filtering, request conflicts, disabled billing, server-fixed Paddle/Stripe pricing, unsigned-webhook rejection, mode checks, Paddle order binding and approved-only refund handling. No real Paddle sandbox or Stripe test transaction, merchant onboarding, or hosted auth/storage integration was completed here. Deno's native type check and targeted ESLint checks also passed.

Repeatable local commands:

```text
npm run test:run -- --config supabase/tests/vitest.backend.config.ts
npm exec --yes --package deno -- deno test --allow-env supabase/tests/edge-auth.deno.ts
npm exec --yes --package deno -- deno check supabase/functions/tailor-cv/index.ts supabase/functions/get-entitlement/index.ts supabase/functions/create-checkout/index.ts supabase/functions/paddle-webhook/index.ts supabase/functions/stripe-webhook/index.ts
```

Monitor failed function calls by error code, webhook delivery failures, remaining credits and purchase/refund reconciliation. Do not log signed document URLs, extracted CVs, bearer tokens, raw Stripe bodies or full email addresses. A deployment is not complete until the hosted signup/upload/pack/payment journey passes the staging checklist.
